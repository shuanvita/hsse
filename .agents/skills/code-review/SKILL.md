# Nuxt + FSD Code Review

Проводи ревью по критериям ниже. Не переписывай код сам, если об этом не просили: находи проблемы, объясняй, предлагай исправление.

## Порядок работы

1. Определи объём: diff/PR (`git diff <base>...HEAD`), указанные файлы или весь слайс. Если объём не указан, ревьюй изменения текущей ветки относительно основной.
2. Определи структуру проекта: где лежат слои FSD (`src/` или корень), как подключены `pages/`, `layouts/`, `middleware/`, `plugins/` Nuxt, есть ли конфиги ESLint/Steiger/boundaries и Tailwind.
3. Пройди критерии по разделам 1-8. Для каждого найденного замечания укажи файл и строку.
4. По возможности запусти проверки (`eslint`, `vue-tsc --noEmit`, `steiger`, тесты) и учти их результат, но не выдумывай результат, если запустить не получилось.
5. Выдай отчёт в формате из раздела «Формат ответа».

## 1. Архитектура FSD

**Слои и импорты**
- Импорты идут только вниз: `app → pages → widgets → features → entities → shared`.
- Нет импортов между слайсами одного слоя (feature не импортирует другую feature).
- Импорт только через публичный API слайса (`index.ts`), без обращения к внутренним файлам.
- Нет циклических зависимостей.

**Размещение кода**
- `shared`: только переиспользуемое и не знающее о бизнесе (UI-кит, утилиты, api-клиент, конфиги).
- `entities`: бизнес-сущности (user, product) и их базовые UI/модель.
- `features`: пользовательские сценарии с действием (добавить в корзину, авторизация).
- `widgets`: самостоятельные блоки страницы, композиция features и entities.
- `pages`: только сборка из виджетов, без бизнес-логики.
- Нет «свалки» в `shared`: бизнес-логика, нужная двум фичам, поднимается вверх или уходит в entity.
- Сегменты `ui`, `model`, `api`, `lib`, `config` используются по назначению.

**Интеграция с Nuxt**
- `pages/`, `layouts/`, `middleware/`, `plugins/` Nuxt остаются тонкими обёртками над слоями FSD.
- Нет бизнес-логики в `app/` и в роутинге Nuxt.

## 2. Чистота кода

- Функция или компонент решает одну задачу (SRP).
- Нет дублирования (DRY), но и нет преждевременных абстракций.
- Нет мёртвого и закомментированного кода, `console.log`, неиспользуемых импортов и переменных.
- Нет магических чисел и строк: константы вынесены и названы.
- Ранние возвраты вместо лестниц `if/else`, небольшая вложенность.
- Функции короткие; 3+ аргумента заменены объектом.
- Побочные эффекты изолированы и предсказуемы.
- Ошибки обрабатываются осмысленно: нет пустых `catch` и проглоченных ошибок.
- Нет хардкода URL, ключей и окружения: всё через `runtimeConfig`/env.

## 3. Читаемость

- Имена раскрывают намерение (`isLoading`, `fetchUserProfile`, а не `flag`, `getData`).
- Единый стиль: компоненты в PascalCase, composables с префиксом `use`, булевы с `is/has/can`.
- Нет сокращений, понятных только автору.
- Единый порядок в SFC и внутри `script`: импорты, props/emits, состояние, computed, методы, хуки.
- Файл не разрастается (ориентир: компонент до ~200-300 строк, иначе предложи декомпозицию).
- В шаблоне нет сложной логики: всё сложнее простого условия вынесено в `computed`.
- Комментарии объясняют «почему», а не «что».

## 4. Vue 3 / Nuxt

- `<script setup lang="ts">` и Composition API.
- Props и emits типизированы (`defineProps<{...}>()`, `defineEmits`); props не мутируются.
- `ref`/`reactive` выбраны осознанно; большие неизменяемые данные в `shallowRef`.
- `computed` вместо `watch`, где можно; у `watch` нет лишних `deep`/`immediate`.
- `useFetch`/`useAsyncData` с уникальными ключами; нет двойных запросов на SSR и клиенте.
- Нет обращений к `window`/`document` вне `onMounted` или `import.meta.client`; нет риска hydration mismatch.
- `v-for` с корректным `:key` (не индекс для изменяемых списков); нет `v-if` вместе с `v-for` на одном элементе.
- Pinia-сторы маленькие и привязаны к слайсу; нет глобального «стора на всё».
- Тяжёлые компоненты загружаются лениво (`Lazy*`, `defineAsyncComponent`); `NuxtImg`/`NuxtLink` вместо нативных `img`/`a`.
- На страницах есть `useHead`/`useSeoMeta`.

## 5. TypeScript

- Нет `any`, необоснованных `as` и `!`.
- Типы лежат рядом со слайсом (`model/types.ts`); типы API не размазаны по проекту.
- Ответы API и возвращаемые значения composables типизированы.
- `interface`/`type` используются единообразно; нет дублирующихся типов.

## 6. Tailwind: лишние классы

Это отдельный обязательный проход по каждому изменённому шаблону.

- Нет дублирующихся и конфликтующих классов (`p-2 p-4`, `flex block`, `text-sm text-base`).
- Нет классов, не дающих эффекта: значения по умолчанию (`flex-row`, `font-normal` без родительского жирного, `block` на блочном элементе, `w-full` на блочном элементе без нужды).
- Нет breakpoint-классов, повторяющих базовое значение (`text-sm md:text-sm`).
- Повторяющиеся наборы классов в 3+ местах вынесены в компонент (предпочтительнее), а не в `@apply`.
- Вместо произвольных значений (`w-[13px]`, `text-[#ff0000]`) используются токены темы.
- Порядок классов единый (`prettier-plugin-tailwindcss`).
- Tailwind и scoped-стили не решают одну и ту же задачу одновременно.
- Нет динамической конкатенации (`bg-${color}-500`): только полные имена классов или map.
- Условные классы читаемы: массив/объект в `:class` или `cva`/`tailwind-merge`, а не длинные тернарники в строке.
- `hover:`, `focus-visible:`, `dark:` и адаптивные префиксы добавлены только там, где нужны, и не дублируются.

При замечании по Tailwind показывай, какие именно классы убрать или заменить.

## 7. Производительность и доступность

- Нет лишних перерендеров и тяжёлых вычислений в шаблоне.
- Нет больших зависимостей ради одной функции.
- Семантическая разметка, `alt` у изображений, `aria-*` у интерактивных элементов, видимый фокус.
- Формы с `label`, работает клавиатурная навигация.

## 8. Тесты, безопасность, процесс

- Критичная логика (`model`, `lib`) покрыта тестами; тесты читаемы и независимы.
- Секреты не попадают на клиент; пользовательский ввод не уходит в `v-html` без санитизации.
- ESLint, Prettier, `vue-tsc` проходят без предупреждений.
- Границы слоёв FSD контролируются инструментом (Steiger, `eslint-plugin-boundaries` или аналог).
- PR небольшой и по одной теме; для UI-изменений есть скриншоты.

## Приоритеты замечаний

- **blocker**: нарушения архитектурных границ FSD, баги, SSR/hydration-проблемы, утечки секретов, XSS.
- **major**: нейминг, структура, типизация, дублирование, нарушения практик Vue/Nuxt.
- **nit**: лишние Tailwind-классы, порядок классов, стилистика.

## Формат ответа

1. **Итог** (2-3 предложения): можно ли мержить и что главное исправить.
2. **Замечания**, сгруппированные по приоритету (blocker → major → nit). Для каждого:
   - `путь/к/файлу.vue:строка`: что не так и почему это важно;
   - как исправить (короткий пример кода или список классов к удалению).
3. **Что сделано хорошо** (по желанию, 1-3 пункта).
4. **Проверки**: какие команды запускались и их результат; что не удалось проверить.

Правила:
- Не придирайся к тому, что уже исправляет линтер или форматтер, кроме случаев, когда они не настроены.
- Не предлагай переписывание без причины; каждое замечание должно объяснять последствия.
- Если критерий не применим к проекту (например, нет Pinia), пропусти его молча.
- Если контекста не хватает для вывода (неясна структура слоёв, нет конфигов), так и скажи, а не угадывай.
